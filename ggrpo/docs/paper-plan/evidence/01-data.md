# Evidence: 01-data (deep-research output, Oct 24, 2026)

Raw synthesis of the 3-vote verified claims. Fields: confidence | claim, SRC (sources), EV (evidence and vote). Sections after the findings: caveats, open questions, refuted claims, sources, stats.

SUMMARY: Few large public C sources come with complete real tests. Two are the best routes. The first is open-r1/codeforces filtered to official_tests_complete == True. The 'verifiable' subset of 8,760 problems also contains problems whose only full oracle is a set of tests generated by DeepSeek-R1. The second is AOJ, whose full system test cases can still be downloaded without a login (checked live 2026-10-24). Project CodeNet ships only the sample I/O from problem statements, which exists for about 51% of problems, so it needs the official AOJ/AtCoder data added to it. ExeBench I/O pairs are generated automatically, with type-guided random inputs and the reference function's output as the oracle, so ExeBench belongs to the synthetic or reference-as-oracle arm, not the real-tests corpus. Neural decompilation and lifting work mostly uses the compiled reference as the oracle. The methods are differential I/O on a finite set of inputs (SLaDe, Forklift via ExeBench IO), branch-profile equality on OSS-Fuzz seed corpora (DecompileBench), symbolic equivalence against the binary (D-LiFT) and an exact match of the recompiled, normalized assembly (Echo). For SFT at scale, the documented corpora are expanded AnghaBench (~4M functions, SLaDe), Forklift (~2.7M functions with x86/ARM/RISC-V assembly from Clang and GCC) and Decompile-Bench (2M pairs, MinHash-LSH dedup, Linux x64 Clang-19 only). The dedup methods described are token hashing and MinHash-LSH. The licenses of the judge sources are still unverified.

- high | open-r1/codeforces: more than 10k unique problems (default split 9,556 train / 468 test). The 'verifiable' subset has 8,760 problems (8,338 train / 422 test). The test split covers contests 1993-2067 (late 2024 to early 2025) and the card asks users not to train on it. That makes it a held-out set for models trained before late 2024, such as Qwen2.5-Coder.
  SRC: https://huggingface.co/datasets/open-r1/codeforces/blob/main/README.md
  EV: Vote 3-0. The verifier checked the counts against the README and the HF datasets-server /size endpoint, and sampled all 468 test rows: contest_id is 1993-2067 and contest_start_year is 2024/2025. The 'lower contamination' reading holds only for models whose pretraining cutoff is before late 2024. Codeforces problems and their public solutions may be in the pretraining data of 2025+ models.

- high | Only open-r1/codeforces problems with official_tests_complete == True have a complete real oracle. Codeforces truncates visible tests to about 400 characters. 'verifiable' = executable AND (official_tests_complete OR generated_tests). The generated tests come from generators written by DeepSeek-R1, and their expected outputs come from correct human solutions; tests where those solutions disagreed were removed. The card does not say how many problems have official_tests_complete set (a repo note gives about 890; this synthesis did not verify that number).
  SRC: https://huggingface.co/datasets/open-r1/codeforces/blob/main/README.md
  EV: Votes 3-0 and 3-0. The card defines official_tests as the tests that are not truncated (under about 400 chars), official_tests_complete as 'no test case was truncated', and executable as 'at least 3 human solutions pass official_tests'. About 30% of problems need custom checkers (from the card). Problems with the flag set to False still carry partial official tests. So the filter is the strict reading of 'complete real tests', not of 'any real tests'.

- high | No bulk route for Codeforces hidden tests was found other than open-r1. online-judge-api-client (last release 10.10.1, Aug 2022) can download Codeforces sample cases but not system cases. For AOJ, it can download both sample and full system cases. Its AOJ path uses judgedat.u-aizu.ac.jp/testcases/{id}/header and then /{serial}/in and /{serial}/out.
  SRC: https://pypi.org/project/online-judge-api-client https://github.com/online-judge-tools/api-client
  EV: Votes 3-0 and 3-0. The verifier read the README table and the source (codeforces.py has only download_sample_cases; aoj.py has download_system_cases). It also tested the AOJ endpoint live on 2026-10-24 without a login. DSL_2_A lists more than 15 named judge cases, and a 1,177,793-byte input downloaded in full, matching the header sizes. The endpoint is undocumented and has a 1 GB per-case limit. The tool may be unmaintained. AOJ's terms for redistribution or training were not checked.

- high | Project CodeNet has 13,916,868 submissions over 4,053 problems (5 of them empty) in 55 languages. 95% of submissions are in C++, Python, Java, C, Ruby or C#, and the text gives no separate count for C. Its built-in oracle is only the sample I/O taken from problem statements 'when available'. The paper reports test data for 51% of problems, and an independent paper (PROBE) finds that most problems have one test. Real oracles need the official AOJ/AtCoder test data, fetched separately.
  SRC: https://github.com/IBM/Project_CodeNet https://arxiv.org/abs/2105.12655
  EV: Votes 3-0 and 3-0. Verified against the README text and the CodeNet paper (abstract and Table 5: 'Percentage of problems with test data: 51%'). A separate claim was refuted 0-3: that all submissions come from AIZU/AtCoder with every problem graded on stdin/stdout, and that the per-source split is in a spreadsheet. Do not rely on that claim. The pie charts in the README (possibly with C's share) were not inspected.

- high | ExeBench v1.01 splits (in functions): train_not_compilable 2.357M, train_synth_compilable 2.308M, train_real_compilable 0.675M, train_synth_simple_io 0.550M, train_real_simple_io 0.0438M, train_synth_rich_io 0.0973M, valid_synth 5k, valid_real 2.133k, test_synth 5k, test_real 2.134k. 'Real' and 'synth' describe how dependencies were resolved (heuristically inferred real #includes vs Psyche-C type inference), not where the tests came from. Only about 44k training functions with real dependencies have I/O, against about 647k with synthetic dependencies.
  SRC: https://huggingface.co/datasets/jordiae/exebench https://github.com/jordiae/exebench
  EV: Vote 3-0. The counts match the HF card and the GitHub README exactly. Each split has its own tarball. The paper's v1.00 counts (4.5M compilable / 700k executable) differ, so cite these numbers as v1.01. The card does not say explicitly that simple_io and rich_io are disjoint; their sum (about 691k) fits the paper's figure of about 700k.

- medium | ExeBench I/O pairs are generated by machine, not human or official tests, so ExeBench fails the real-tests rule. Inputs are random and guided by the function signature (FACC JSON type descriptions, arrays default to size 32, undefined globals randomized), with 10 IO pairs x 3 seeds = 30 per function. Outputs come from running the compiled reference function. ExeBench's own contributions (I/O, harness) are MIT. The C functions keep the license of their original repositories. Only about 16% of executable GitHub functions produced 'rich' (non-constant, non-identity) I/O.
  SRC: https://huggingface.co/datasets/jordiae/exebench https://doi.org/10.1145/3520312.3534867 https://arxiv.org/abs/2502.04536
  EV: Vote 2-1. The dissent targets the claim's statement that 'the card does not say' how I/O was made; the card's citation abstract does mention 'scalable generation of IO examples'. The verifier confirmed the generation method from the MAPS 2022 paper itself, and the Idioms paper also calls the tests automatically generated. The conclusion (synthetic, reference-as-oracle I/O) is strongly supported. Only the claim's description of the card was slightly wrong.

- high | LLM4Decompile's HumanEval-Decompile oracle is re-executability: the output must compile, run and pass all predefined test assertions. Its assembly comes from GCC on Linux x86_64 at O0-O3, through gcc then objdump -d. The prompts therefore cannot be reused for GG's clang/macOS x86 to ARMv8 setup. The C sources and asserts have to be recompiled.
  SRC: https://github.com/albertan017/LLM4Decompile
  EV: Vote 3-0. The README describes re-executability, GCC O0-O3, the preprocessing script and the file decompile-eval-executable-gcc-obj.json. It mentions no clang and no ARM. A separate claim was refuted 0-3: '164 functions x 4 = 656, README silent on MBPP-C and on the origin of the asserts'. Do not cite it. The exact objdump flags of the published file come from the example script, not from a direct statement.

- high | Decompile-Bench (NeurIPS 2025 D&B) is an SFT-scale corpus without tests. It has 2M binary-source function pairs, kept from 100M collected pairs (about 2%). It comes from 3,961 permissively licensed C/C++ repositories in The Stack v2 (Blue Oak Council approved or ScanCode 'Permissive'), giving about 450 GB and 85K binaries. Everything is built with a patched Clang-19, Linux x64 only, at O0-O3. Its filtering is an example of dedup practice: a project-scope filter (about 45% header functions dropped), in-binary dedup (about 20%) and cross-binary MinHash-LSH (about 32%). ARM and RISC-V targets would need recompiling from the same sources.
  SRC: https://arxiv.org/abs/2505.12668 https://huggingface.co/datasets/LLM4Binary/decompile-bench
  EV: Votes 3-0 and 3-0, checked against the full paper (Secs 3.1, 3.2, 5.1). The paper names no other target ISA. Its training is one epoch of SFT on 10% of the data; there is no RL. The HF card lists cc0-1.0 and the columns name, code, asm and file. The paper itself gives no dataset license.

- high | Decompile-Bench-Eval runs re-executability tests only on HumanEval and MBPP. The authors translated these to C/C++ by hand and run the original tests at O0-O3. The leakage-control split GitHub2025 (121 repositories created in 2025 or later, about 60K functions, with third-party, external and submodule directories removed) has no real test oracle. The authors say they could not reliably automate compiling and running real-world projects.
  SRC: https://arxiv.org/abs/2505.12668
  EV: Vote 3-0. Sec 4.1 and Sec 5.3.1 show the scope of re-executability. GitHub2025 is reported only with R2I, edit and embedding similarity, CodeBLEU and GPT-judge. Appendix G states that re-executing real-world projects is still an open challenge.

- high | DecompileBench (arXiv 2505.11340) offers a pool of real functions that come with real inputs, using the compiled reference as the oracle. It has 23,400 functions from 130 OSS-Fuzz projects, chosen by coverage: fuzzers run on their seed corpora under Clang coverage instrumentation, clang-extract pulls out each covered function, and each is compiled to a .so. To check a function, the original compiled function and then the decompiled one are swapped into the program and run on the same seed corpus. Correct means strictly equal whole-program branch-execution profiles (SanitizerCoverage; the metric is the Coverage Equivalence Rate), not passing unit tests.
  SRC: https://arxiv.org/html/2505.11340v1 https://github.com/Jennieett/DecompileBench
  EV: Votes 3-0 and 3-0. The paper and the repo describe the same pipeline. Caveats: (1) the inputs are harness-level fuzz seeds, not argument vectors for each function, so the project build and the harness are needed; (2) OSS-Fuzz build scripts pull the latest commit, so a rebuild may give different functions; (3) there is no prebuilt release and no license section; (4) C vs C++ is not stated, only implied by the tooling; (5) seed counts are not reported.

- high | In neural decompilation and lifting, the usual oracle is differential I/O against the compiled reference on a finite set of inputs, and the inputs come from elsewhere. SLaDe (CGO 2024) recompiles the decompiled function, puts it back into its original calling program and requires the same program state as the original assembly. It counts non-termination as non-equivalence and says it is the first to use this compiler-testing method on neural decompilation. Its inputs are ExeBench IO and the Synth benchmark. Forklift uses observational equivalence on unit tests and checks return values plus side effects on arrays, struct pointers and globals. It assumes reference unit tests already exist (in practice ExeBench's generated IO) and does not generate new inputs.
  SRC: https://arxiv.org/pdf/2305.12520 https://arxiv.org/html/2404.16041v1
  EV: Votes 3-0 and 3-0. SLaDe Sec III-A uses 'input/output equivalence on finite subsets F ⊆ D', and Sec VII-A.2(d) puts the function back into the calling program. Forklift Sec 3.3 says 'We opt for observational equivalence, i.e., unit tests' and 'We assume that the desired functions have reference unit tests'. Neither paper fuzzes against the reference binary. Their inputs are the type-guided random inputs ExeBench already made.

- high | Some oracles use no test inputs. D-LiFT (NDSS 2026) uses the original binary as the oracle through symbolic execution. Arguments become symbolic, angr 9.2 and z3 4.13 compare return-value models with a 30 s timeout, external calls are counted per path, and code that fails to recompile gets a -3 penalty. The authors exclude fuzzing because the reward must be deterministic, and exclude unit tests and Alive2 because they depend on the source. The checker is approximate: 80.7% of functions (1,573/1,948) get a result, and precision 0.91 / recall 0.9785 was measured on only 100 functions. Echo (Sep 2026) uses an exact match between the normalized recompiled assembly and the target as its main, compiler-backed correctness signal. Its behavioral-equivalence metric depends on harnesses that the benchmarks supply. The authors say such harnesses are generally missing for real-world binaries, and the Mirai evaluation reports only match rate and edit distance.
  SRC: https://arxiv.org/html/2506.10125v2 https://arxiv.org/abs/2609.18706
  EV: Votes 3-0 for each of the four sub-claims. One sub-claim had medium verifier confidence: that Mirai uses only exact match because no harnesses exist. The paper implies this reason but never states it. The D-LiFT exclusion passage is the same in v4 (17 Aug 2026). Inference, not verified: exact match is a natural target for matching decompilation, but a correct x86 to ARM translation has many valid outputs. For transpilation, an Echo-style check would at most be a sufficient condition, not a usable reward on its own.

- high | Documented SFT corpora for assembly translation and decompilation: (a) SLaDe uses an expanded AnghaBench of about 4M real-world C functions with function-level assembly from ExeBench (GCC, O0 and O3, x86 and ARM), deduplicated against the test set by token-level hashing. (b) Forklift has about 2.7M parallel functions built on ExeBench, with assembly from Clang and GCC at O0/O3/Oz for x86, ARM and RISC-V plus LLVM IR. Its filtering is token-based C dedup, assembly-based dedup, removal of eval leakage and length filtering. (c) Decompile-Bench has 2M pairs after MinHash-LSH (see above). Forklift is the closest existing corpus to GG's need: assembly for x86, ARM and RISC-V from the same C functions.
  SRC: https://arxiv.org/pdf/2305.12520 https://arxiv.org/html/2404.16041v1 https://arxiv.org/abs/2505.12668
  EV: Votes 3-0, 3-0 and 3-0. Forklift gives no split of the 2.7M by ISA or optimization level, so it is unclear whether 2.7M counts C functions or (function, ISA, opt) tuples. Its model translates only to LLVM IR. SLaDe trains one model per ISA and optimization level. Whether the Forklift and SLaDe corpora are publicly released, and under what license, was not verified.
